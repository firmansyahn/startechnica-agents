# The OpenAPI document

## Where it lives and who owns it

- **One document per API surface** (`console`, `public`, `internal`), because surfaces differ in auth, audience and stability. File: `<module-root>/api/<surface>.openapi.json` ([go-project-layout](../../go-project-layout/SKILL.md): `/api` holds API specs).
- **OpenAPI 3.1.x.** Its schemas are JSON Schema 2020-12: `type: ["string", "null"]` instead of 3.0's `nullable`, `const`, `examples`. Tooling that only speaks 3.0 is the wrong tooling.
- **The backend owns it.** A frontend developer who needs a new field asks for (or writes) the backend change; the frontend never patches its copy.
- **Committed, both the source and the frontend's copy**, so the web image builds from the app folder alone and a diff shows every contract change in review.
- JSON, not YAML, when the document is generated: stable key order (sorted), no anchors, readable by `import spec from "./x.openapi.json"`.

## Code-first (default)

The Go route table is already where each route is declared (method, path, handler, permission). Extend it with the request and reply types, and generate the document from it:

```go
// internal/api/console/items/routes.go
func Routes() []httpx.Route {
	return []httpx.Route{
		{Method: "GET", Path: "/items", Handler: list, Permission: "items.read",
			Summary: "List items", Query: ListQuery{}, Reply: httpx.Page[Item]{}},
		{Method: "PATCH", Path: "/items/{id}", Handler: patch, Permission: "items.write",
			Summary: "Change an item", Body: ItemPatch{}, Reply: Item{}, Errors: []int{404, 409, 422}},
	}
}
```

```go
// internal/app/openapi_test.go
var update = flag.Bool("update", false, "rewrite api/*.openapi.json")

func TestOpenAPI(t *testing.T) {
	for _, s := range surfaces {
		got := openapi.Build(s.Name, s.Routes())          // reflects the types into JSON Schema
		path := filepath.Join("..", "..", "api", s.Name+".openapi.json")
		if *update {
			writeJSON(t, path, got)
			continue
		}
		want := readFile(t, path)
		if diff := cmp.Diff(string(want), marshal(got)); diff != "" {
			t.Fatalf("%s is stale; run go test ./internal/app -run TestOpenAPI -update\n%s", path, diff)
		}
	}
}
```

- The schema of a type comes from its `json` tags ([go-code-style](../../go-code-style/SKILL.md): the tag is the contract), `omitempty` makes a field optional, a pointer or an `Opt[T]` makes it nullable, and an enum type lists its values (`Enum() []string`). Use a reflector library or a small in-house one; whichever, it must emit 3.1.
- Doc comments become `description`s; a route's `Errors` list becomes its documented refusals, all pointing at one shared `Failure` response.
- A route without reply types fails the test, so nothing new escapes the document.
- **Keep it honest:** handler tests validate their replies against the generated document ([contract-tests.md](contract-tests.md)). A generator only proves the types were declared, not that the handler returns them.

## Spec-first

Write the document by hand (or in a design tool), then generate server stubs and types from it, or validate requests and replies against it in middleware. Choose it when the API is designed before the backend exists or is shared with outside parties.

- **Keep it honest:** the server either compiles against generated interfaces (a missing handler doesn't build) or runs a request/response validator in tests and in non-production environments.
- **Check 3.1 support before adopting a Go library.** Generators and validators differ: some target 3.0 only, some accept 3.1 partially. Run the candidate against your actual document (nullable unions, `const`, `$ref` siblings) before choosing it, and pin its version.
- Lint the document in CI (a 3.1-aware linter such as Redocly or Spectral) for missing descriptions, operation ids and error responses.

## The frontend's copy and types

```js
// <app-root>/scripts/gen-api.mjs (yarn gen:api; yarn gen:api --check in CI)
import { readFile, writeFile } from "node:fs/promises";
import { fileURLToPath } from "node:url";
import openapiTS, { astToString } from "openapi-typescript";

const source = new URL("../../<module-root>/api/console.openapi.json", import.meta.url);
const copy = new URL("../src/api/console.openapi.json", import.meta.url);
const types = new URL("../src/api/schema.gen.ts", import.meta.url);
const HEADER = "// Generated by yarn gen:api from the backend's console.openapi.json; do not edit.\n\n";

const spec = await readFile(source, "utf8");
const generated = HEADER + astToString(await openapiTS(JSON.parse(spec), { alphabetize: true }));

const check = process.argv.includes("--check");
const stale = [];
for (const [url, want] of [[copy, spec], [types, generated]]) {
  const have = await readFile(url, "utf8").catch(() => null);
  if (have === want) continue;
  if (check) stale.push(fileURLToPath(url));
  else await writeFile(url, want);
}
if (stale.length) {
  console.error(`Stale; run yarn gen:api and commit:\n  ${stale.join("\n  ")}`);
  process.exit(1);
}
```

- `openapi-typescript` (7.x) exports `openapiTS` and `astToString`; its CLI has `--check`, `--alphabetize`, `--enum-values` (enum value arrays for selects) and `--read-write-markers` (`readOnly`/`writeOnly` fields). The script form above also checks the copied document, which the CLI's `--check` doesn't.
- `"gen:api": "node scripts/gen-api.mjs"` in `package.json`; run through Yarn ([nextjs-package-manager](../../nextjs-package-manager/SKILL.md)).
- In a monorepo, put the generated types in a package (`packages/api-types`) when two apps use the same surface.
- Use the types by name: `type Item = components["schemas"]["Item"]`; query parameters from `operations["listItems"]["parameters"]["query"]`. Re-export the common ones from one `src/api/types.ts` so imports stay short.

## CI

| Job | Fails when |
|---|---|
| Backend `go test ./...` | The document differs from what the route table generates; a handler's reply doesn't match it |
| Frontend `yarn gen:api --check` | The frontend's copy or `schema.gen.ts` differs from the backend's document |
| Frontend `yarn tsc --noEmit` | Code uses a field the new types no longer have |
| Optional: breaking-change diff | A merge request removes or retypes something without a deprecation (an OpenAPI diff tool against the target branch's document) |

In a repo with both sides, one merge request changes the route, regenerates the document and the frontend copy, and adapts the frontend; CI proves all three agree.

## Versioning and deprecation

- **Additive changes need no version:** a new endpoint, a new optional request field, a new reply field, a new enum value the client renders with a fallback.
- **Breaking:** removing or renaming a field or endpoint, changing a type or format, making an optional request field required, narrowing accepted values, changing a status code's meaning.
- Break in steps: add the new shape, mark the old `deprecated: true` (with a `description` naming the replacement and the removal date), move the clients, then remove. A public API also answers `Deprecation` and `Sunset` headers on deprecated operations.
- A surface version lives in the path (`/api/v1/...`); `v2` is for a redesign, not for one renamed field. A first-party console behind a BFF that ships with its backend can break in one merge request instead, since both sides ship together; say so in the project's API guide. Even then, a rolling deploy runs old and new side by side for a few minutes, so a removed field must not crash the old frontend (render a fallback) and a newly required request field needs a default for one release.
- Operation ids are stable names (`listItems`, `patchItem`); generated clients and docs key on them.
